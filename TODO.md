# GA implementation specification

Implement section 1 before publishing new specializations and sections 2/3 before certifying migrated candidates. Section 2 is not a prerequisite for fresh candidates when no old run is being reused. Sections 4/5 repair acquisition and read-only deployment behavior; section 6 requires measurement before performance claims. Do not start the primary printer/support fit before section 7's source, review and cadence requirements are resolved. An identity/schema revision alone does not invalidate compatible weights; reconstruction must establish which computations actually changed. Keep the existing bounded DSL, immutable Plan/mutable Call, effective SelectionState, per-target LabelSource, explicit ModelJob, single hosted engine, leased JSONL Journal and frozen deployment receipt. Extend these owners and repair their consumers; do not add another runtime, family resolver, metric implementation, transport or persistence engine. Preserve full-vocabulary loss v2 and its independent numerical reference tests.

Model loading, downloads, hosted inference, conversion, fitting and hardware measurements remain explicitly invoked jobs. Editing this specification does not start them. Run one model job per host; see `bench/README.md`, *Running model jobs*.

## 1. Freeze every input that can change deployed behavior

- [x] Owners: core task materialization, `semantic_switch.tools.deployment.freeze_specialization`, trainer prepare/select and receipt lineage validation.

**Invariant:** a specialization is a frozen decision system, not merely a GGUF. Its task, resolved guidance, exact corrections, policies and model identity come from declared inputs. Adding a working-tree correction after preparation cannot silently change the deployment. Selection remains judge-only model ranking; the receipt and final check must identify the complete application behavior separately.

1. Extend the existing core task materialization boundary to return a serializable frozen task record: canonical compiled definition, resolved guidance text/content digests, observed target meaning revisions and the effective exact-correction records with their LabelSource histories and family seeds. Reuse compilation, example collection, canonicalization and FamilyIndex. Store the bundle under the prepared job directory using existing immutable payload publication; include its file hashes and behavior digest in the resolved job. No serialized Plan/Snapshot objects, second renderer or second source-assignment algorithm.
2. Resolve corrections once during preparation from authored examples and the declared sidecar. Persist the effective examples selected by the existing collection semantics. An empty population stays empty. Include only behaviorally active overrides in the override population; `exact_override: false` makes them inactive. Later changes to source paths, guidance or sidecars require new preparation, rather than being picked up during fitting/select. The frozen compiled task must reproduce the exported observed meanings and presentations before a job is admitted.
3. Add an explicit `override` use to the existing canonical provenance membership contract and its receipt validators. Reuse observation addresses/projections, canonical family closure and label-source identities; merge uses for an observation already declared for adaptation/selection/acceptance_fit rather than duplicating its row. Overrides are an application use, not a new tuning role. Validate source/family/label consistency and reject incompatible duplicate declarations. Check overlap accounting must include override evidence independently of whether the particular check execution ultimately chooses the example or judge source.
4. Native candidate ranking still uses `sources=('judge',)` and clearly reports that scope. Execute it against the frozen task/guidance. Freeze policies and the lock from that same materialization and its explicitly recorded correction population; remove discovery of ambient `.examples.jsonl` from freeze. Core owns internal Example construction and lock assembly. Preserve the current caller-owned staging, ModelJob participation, identity comparison, receipt validation and atomic directory publication.
5. Keep fitting identity restricted to numerical fitting inputs. Changes to the override population alter deployment behavior identity; changes to resolved guidance alter fitting/monitoring identity when they change presentations. Receipt definition/guidance/override hashes must agree with the staged lock and task. Failure before publication leaves no deployment. Preserve immutable originals and audit history when replacing old deployments; an old receipt with undeclared active overrides cannot certify disjointness until its embedded examples have been reconciled with recorded source/family evidence.
6. Verification: prepare → fit fixture → add a `report 999` correction → select must either use the prepared correction population unchanged or reject changed inputs; it cannot publish `continue` from an undeclared example while its selected judge answers `escalate`. Exercise authored examples, empty overrides, inactive overrides, multiple label histories and overlapping check families. Change a referenced guidance file without editing the top-level YAML; a frozen job must retain its original guidance or reject the changed source. Remove/move original source files and verify a complete frozen job/deployment remains loadable. Verify public decisions and provenance after publication through Runtime.from_specialization.

## 2. Prove adapter configuration equivalence during migration

- [x] Owners: `semantic_trainer.migrate`, shared trainer conversion validation and candidate readers.

**Invariant:** a hash calculated during migration records current bytes; it does not prove those bytes describe the fitted adapter. Adapter weights, scaling/configuration and pinned base jointly identify the candidate.

1. Keep the bounded migration of the immediately preceding supported loss-v2 schemas. Parse `adapter_config.json` as a validated object before creating compatibility evidence. Normalize the supported vanilla-LoRA configuration against the recorded fitting recipe and resolved targets: adapter type, rank, alpha/scaling, dropout, target modules, bias/modules-to-save settings, orientation and supported rank/alpha patterns. Reject alternate LoRA variants or unsupported behavior-affecting settings. Compare base/config identity against the original pinned assets. Reuse one configuration validator for migration and conversion; current-schema candidates additionally retain their recorded configuration hash check.
2. Reconstruct omitted fields only from documented defaults of the recorded supported PEFT version/profile. A missing field with no established default is missing equivalence evidence, not permission to use the currently installed library's default. Normalize path aliases without treating them as model identity; validate the referenced base content through section 3. Preserve original configuration and weight files unchanged.
3. Only after semantic equivalence passes, record both configuration/weight hashes and the normalized configuration digest in the compatibility record. The normal select path rechecks these identities, the original resolved-job digest and the reconstructed fitting/monitoring identities. A post-migration edit invalidates the record. Preserve specific errors for configuration drift, weight drift, unavailable assets and insufficient historical evidence; do not turn every failure into an unconditional refit instruction.
4. Verification: an old candidate whose `lora_alpha` changes to 999 must not return `eligible: true`, even when weights and shapes are unchanged. Also change rank, target modules, orientation, adapter variant, rank/alpha patterns and modules-to-save. Equivalent supported default/path representations pass; unavailable defaults fail explicitly. Exercise migration → accepted compatibility → normal select, using realistic complete PEFT configurations rather than only `{"r": 2}` placeholders. No model download or real fitting is needed.

## 3. Identify the numerical fit and monitoring computations

Include tokenizer identity and the staged-answer/reduction revision. Observation IDs identify evidence/meaning and are insufficient to identify the evaluated token computation. Hash the exact descriptions consumed by the trainer; do not introduce an independently reconstructed prompt representation.
2. Replace the monitoring identity's ID-only populations with descriptions of the actual ordered model_select and training-probe observations. Retain complete-situation composition, cadence, planned points, ranking and stopping settings. Keep acquisition record histories outside numerical identity unless they change the scored population/composition. Canonical family closure remains the separate owner of independence and statistical grouping.
3. Project HF model/configuration/tokenizer content identities from the existing verified asset manifest into fit identity. Repository/revision are useful provenance but cannot substitute for the materialized HF files the loader consumes. Use sorted logical file names and content hashes, excluding installation roots and conversion-binary paths. Preserve the separate quantized native base and conversion toolchain identities. Record actual fitting dependency/profile versions in the run for reconstruction; a matching input digest is not a claim of deterministic execution across devices or library versions.
4. Increment fitting/monitoring identity revisions and affected job/candidate schemas together. For supported legacy migration, reconstruct fit, model_select and probe descriptions from original immutable exports, preserving the original consumed order. Verify every population member is recoverable, with consistent repeated evidence and resolved base/config content. Missing original monitoring presentations or asset evidence means eligibility is unproven. A changed monitor computation preserves compatible adapter weights but invalidates the claim that the old retained shortlist was produced by the new protocol.
5. Keep migration outcomes specific: equivalent metadata/path/family-name repair can preserve eligibility; changed numerical training inputs require a new fit; changed monitoring/ranking evidence requires the new selection protocol and cannot relabel old checkpoint retention; acceptance-only changes rerun policy fitting/freeze; report-only changes recompute supported aggregates. Preserve originals and historical check exposure. Do not add optimizer resume or generic historical readers.
6. Verification: replace only six model_select presentations while preserving observation IDs and situation records; `fit_id` may remain equal, but `monitor_id` must change and the old shortlist cannot be certified eligible. Use genuine alternative exported option permutations and updated presentation IDs so the regression is a valid rendering case. Independently vary selection labels, weights, stage mapping, tokenizer and probe presentations. Change HF weights or config under the same repository/revision; fit identity must change. Relocating identical verified content preserves computation identities. Inspect the numerical records and hand-calculated identity differences, not only schema versions.

## 4. Bound unique acquisition without discarding duplicate lineage

- [x] Owner: `semantic_switch.training.Task.situations`; consumer: trainer collection.

1. Calculate the canonical input key before applying `max_situations`. Reject only insertion of a new key after the unique-population limit is reached. An existing key must still validate role consistency and merge groups, pairs, tags and selection histories through the existing situation-record owner. Compute the key once per row.
2. Keep byte limits independent from unique-situation limits; do not add another persistence engine or remove explicit acquisition bounds. Preserve deterministic record order and source-line diagnostics. Duplicate evidence with conflicting roles fails even at the limit; matching duplicate evidence does not consume another situation.
3. Verification: `a, b, a` with max_situations=2 yields two situations and retains the third row's additional lineage; `a, b, c` fails at line 3. Cover duplicates before/at the limit, conflicting roles, byte overflow and an empty source. Exercise collection materialization as well as the helper.

## 5. Artifact verification does not require a writable hash cache

- [x] Owner: `semantic_switch.files.sha256_file` and the existing hash-cache functions.

1. Return a successfully computed digest even when optional hash-cache lookup/publication fails because of permissions or a read-only filesystem. Cover cache path initialization/mkdir as well as lookup and publication: `cache_dir()` currently creates the directory before the read handler runs. Catch only the relevant cache I/O failures at the cache boundary; artifact open/read/stat failures remain errors. Preserve the existing stat-based cache key and bounded streaming hashing. No second hashing implementation or blanket suppression of OSError.
2. Make only the optimization cache best effort. Journal commits, exposure ledgers, immutable payloads, receipts and published directories retain their existing required durability and error propagation. A read-only deployment may validate and execute readable artifacts without creating cache files; it must still reject a changed artifact.
3. Verification: compare an uncached readable artifact's digest against hashlib with cache lookup/write raising PermissionError and EROFS. Receipt validation and fake-backend deployment loading must succeed with read-only cache storage. Missing/unreadable artifacts and content mismatches still fail; ordinary writable-cache reuse and invalidation remain correct.

## Integration order and subsystem boundaries

| Boundary | Canonical owner/representation | Remaining work |
| --- | --- | --- |
| source evidence → assigned observations | envelopes, LabelSource, dataset assignment, FamilyIndex | duplicate-limit repair (4); pack review (7.1, 7.3) |
| assigned observations → prepared cohort | pinned exports, source occurrences, canonical family memberships | freeze effective task/guidance/overrides (1); numerical identities (3) |
| prepared cohort → fitting tensors | loss v2, PackedSlots, explicit recipe/schedule, Monitor/Deadline | reusable prepared inputs and measured cadence (6) |
| execution → benchmark row | Measurement, failure rows, Progress, leased Journal, canonical exact/action metrics | measured public versus diagnostic selection work (6.3) |
| check evidence → independent claim | EvidenceContext, exposure audit, canonical family statistics | override overlap (1); reviewed check/compare runs (7.4) |
| core ↔ trainer | supported task/observation records, core-owned freeze, explicit compatibility records | adapter configuration proof (2); fit/monitor reconstruction (3) |
| selected model → application | verified merge/quantization, frozen receipt, Runtime.from_specialization | declared frozen behavior (1); read-only verification (5) |

For the two primary benchmark runs: pin used sources (7.0) → repair support composition/review protocol and units (7.1/7.2) → implement frozen behavior and complete identities (1/3), with acquisition/cache repairs (4/5) → provisional export/prepare and GPU update/full-monitor profile (6.1) → finish the declared human review, rebuild/reassign and validate profile applicability → final export/prepare with fixed cadence → fit → select → check → matched comparison. Printer runs first, then support, with `MARGIN` predeclared. Source/reference and core contract work can proceed independently; no production fit starts while either still changes its effective inputs. Existing immutable model assets can be reused. Section 2 blocks only reuse of old candidates; no ready primary printer/support fitted run was found under `work` in this review.

The current `daf12a1b…` job and the script's 550-example cadence are provisional. Re-prepare under the final contract and measured cadence before spending the primary five-hour budget. A new schema, review record or export digest makes the old envelope stale, but does not by itself prove that adapter weights are unusable; section 3's reconstruction distinguishes compatible computations from real fitting/monitoring changes. Episodes, seed/rate experiments and transfer follow the two primary comparisons. Preserve the existing core/trainer package split, supported task descriptors and deployment-freeze boundary. Examples use public APIs and receipt-frozen tasks; compiler objects, tensor packing, lock construction and migration plumbing stay outside demo user flows.

Keep the existing single async HTTPX/AnyIO hosted engine with pooled I/O, total elapsed deadlines including queue time, cancellation and a synchronous facade. Keep explicit per-job admission/ownership and one leased execution journal. Add targeted failure tests when these boundaries change; do not reintroduce synchronous/async transport forks, thread-local admission bypasses or SQLite alongside JSONL without a measured requirement that the canonical owner cannot satisfy.

Behavioral verification uses independent numerical references, fake scorers/transports and temporary artifacts. Verify artifact compatibility and failures at boundaries, then run affected runtime/trainer tests. Hardware/provider jobs have their own receipts. Test counts, lints and coverage do not establish numerical correctness, deployment quality or speed.

Excluded: retrieval/ontology services, automatic tools/agents, per-fact model routing, optimizer resume, adapter blending, full-weight fitting, taxonomy growth, dashboards, distributed admission and universal confidence percentages. Keep vanilla LoRA; EMA, soft-label distillation, rank/batch sweeps or alternate methods require a demonstrated reviewed-data limitation. Multimodal ingestion/training requires a separately specified end-to-end evidence/export/runtime contract.

## Applied upstream lessons and primary references

- [PyTorch scatter semantics](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.scatter_.html): preserve unique unpadded membership coordinates and the loss-v2 float64 reference tests. [Performance guidance](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html#avoid-unnecessary-cpu-gpu-synchronization): host scalar/control-flow operations synchronize accelerator work. Section 6 reuses existing completion boundaries and measures full updates/monitor points; synchronization-heavy diagnostic phases do not belong in every production sub-operation.
- [Grouped validation](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data): correlated samples require group-disjoint validation. Preserve the existing connected cohort resolver and include override lineage in section 1; an observation-deduplication key cannot substitute for complete group history. This lesson does not require adding scikit-learn or cross-validation folds. [Threshold tuning](https://scikit-learn.org/stable/modules/classification_threshold.html) keeps acceptance fitting separate from model selection and final checking; grouped validation does not establish representative acquisition.
- [SOP-Bench evaluator](https://github.com/amazon-science/SOP-Bench/blob/main/src/amazon_sop_bench/evaluation/evaluator.py) and [metrics](https://github.com/amazon-science/SOP-Bench/blob/main/src/amazon_sop_bench/evaluation/metrics.py) distinguish submitted task success, execution completion and conditional success. Preserve explicit local outcome/completeness fields and canonical exact/action metrics. Do not copy the upstream inference of completion from error text or its collapsed success flag; typed evidence owns these decisions here. Keep the existing Journal rather than its CSV/trace resume fallbacks. [Construction](https://arxiv.org/html/2506.08119v2), [licence](https://github.com/amazon-science/SOP-Bench/blob/main/LICENSE).
- [τ²-bench environment evaluator](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/evaluator/evaluator_env.py): strict replay, database comparisons and environment assertions assess end state independently from action wording. Section 7 keeps episode terminal assertions separate from action sets. Do not adopt its default reward of 1.0 when criteria are missing; absent criteria or incomplete gold cannot establish local success.
- [Pinned S1MB](https://github.com/hotchpotch/S1MB/tree/39f122bd51d42d21e4ee1ae95974e462fd09a58d) is the compatibility reference for structured criteria, soft targets and evaluator/model revisions. [ABCD](https://github.com/asappresearch/abcd) informs support realism; hidden intent remains outside observable-prefix evidence. [DiagnosticIQ](https://arxiv.org/html/2605.08614v1) informs rule-changing contrasts, not a borrowed accuracy claim.
- [PEFT checkpoint format](https://huggingface.co/docs/peft/developer_guides/checkpoint), [llama.cpp export-lora](https://github.com/ggml-org/llama.cpp/tree/master/tools/export-lora): preserve base/adapter identity through verified F16 → merge → quantize; deployment-native selection remains authoritative. Sections 2/3 validate configuration and original base content before admitting migrated weights. [LambdaLR](https://docs.pytorch.org/docs/2.14/generated/torch.optim.lr_scheduler.LambdaLR.html) and [Transformers schedules](https://huggingface.co/docs/transformers/en/main_classes/optimizer_schedules) support explicitly resolved warmup/total-step inputs.
- [scikit-learn estimator development](https://scikit-learn.org/stable/developers/develop.html) demonstrates interoperability through defined input/state/output behavior rather than copying an implementation. Preserve supported core/trainer operations and behavioral round trips without adopting its estimator framework or test gates.
