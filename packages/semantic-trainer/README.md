# semantic-trainer

Optional fitting package for semantic-switch: lexical heads and task-specific LoRA on the default student. The runtime package never depends on it or on torch.

## Install

The trainer runs in its own environment. Install the torch wheel that matches the fitting device first, then the package; an already installed torch is kept.

| Device | Install |
| --- | --- |
| CPU | `python -m venv .venv-cpu && .venv-cpu/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu` |
| Intel XPU (Arc, Panther Lake) | `python -m venv .venv-xpu && .venv-xpu/bin/pip install torch --index-url https://download.pytorch.org/whl/xpu` |
| NVIDIA CUDA | `python -m venv .venv-cuda && .venv-cuda/bin/pip install torch --index-url https://download.pytorch.org/whl/cu128` (pick the CUDA index matching the driver) |

Then, from the repository root: `<env>/bin/pip install -e '.[local]' -e 'packages/semantic-trainer[lora]'`. Lexical heads only need `semantic-trainer[lexical]`. Tests run from `packages/semantic-trainer` (`<env>/bin/python -m pytest`) against the installed packages plus the repository test support `<env>/bin/pip install -e packages/semantic-testkit`, which neither application wheel ships; tests that also need `bench` live in the repository's `tests/integration`.

Check the device: `<env>/bin/python -c "import torch; print(torch.__version__, torch.xpu.is_available(), torch.cuda.is_available())"`.

## Core contract

The trainer (Python ≥ 3.12, `semantic-switch>=0.26,<0.27`) imports only the public `Runtime`, `Model` and `ConfigError` and the integration module `semantic_switch.training`, which exposes explicit task (`Task`, `describe_task`, `freeze_task`, `admit`), artifact (`read_export`, receipts, bundles), scoring (`Selection`, `model_job`, `gpu_available`) and deployment (`freeze_specialization`, the current pointer) operations. There is no integration revision: every consumed record carries its own schema and the decoder refuses an unsupported one (`read_export`, `decode_request`, receipts) before any model admission. Native exports are normalized: one manifest holds the target and native descriptors, interned token segments and answer groups are referenced by ordinal, and `read_export` verifies the publication once and returns shared presentation views that fitting concatenates and casts only per admitted batch. Pipeline stage reuse binds the installed version, or the source digest of an editable or source checkout, of semantic-switch and semantic-trainer. The trainer never traverses compiled plans or snapshots, constructs internal examples or assembles locks; model execution stays in core and no application runtime imports the trainer.

Inside the trainer, `objective` owns every numerical and input operation (prepared inputs, slot packing, full-vocabulary loss, update and evaluation), `monitor` owns the deadline, monitor points, retention, feasibility and stop record, and `lora` orchestrates fitting and profiling over both; `docs/invariants.md` in the repository lists the invariants each owns.

## Pipeline

```
ss specialize alarms.yaml --examples alarms.labels.jsonl --to work/alarms --trainer /abs/.venv-xpu/bin/semantic-trainer --device xpu:0 --native-device gpu
ss specialize --to work/alarms --cadence 552        # after awaiting_configuration; the same command without SWITCH resumes
```

`ss specialize` writes one immutable versioned `WORK/request.json` (task, guidance, corrections and labels bound by content; base repository/revision or asset manifest; devices, recipe, budget, family selection, profile, deployment representation) and runs the configured absolute trainer executable as an argument vector, after checking its `semantic-trainer protocol` answer. `semantic-trainer pipeline WORK/request.json [--until STAGE] [--attempt N] [--cadence N]` is that one controller: stage progress goes to stderr and exactly one versioned result (state `completed`, `stopped`, `awaiting_configuration`, `failed` or `cancelled`, the current stage and the lock, receipt, profile, job, run, base and environment identities) to stdout; termination cancels the stage and its child processes. The fixed stages are `freeze` (materializes the frozen task bundle, the request's label bytes and one `frozen-inputs.json` manifest of source identities, materialized digests, target scope and assignment into its stage directory, verifying the sources against the request while it reads them; target support, whole-family roles and nonempty model_select are checked before any model loads; every later stage consumes only these verified materialized files, so a resume after freeze never reopens the originals), `assets` (a mutable revision is resolved once and pinned in the journal), `export` (tune split only; check families are refused), `population` (freezes the task bundle into the job directory, assigns whole families to roles, admits label histories and resolves the cadence-free population once: presentations, weights, token counts, recipe, schedule and the `fit` identity), `profile` (measured on that population, or a supplied profile checked against this workload), `cadence` (a decision committed once per request and profile, projected from population counts without rereading exports; without one the controller stops with the measured choices and the resume command), `finalize` (writes the job with the committed cadence and profile and resolves the monitoring plan, `monitor` and job identities over the cached population; a changed cadence changes only this stage and later), `fit`, `select` and `lock` (verification through the receipt loader). A leased pipeline journal bound to the request records each stage's computation key (stage, consumed output identities, resolved settings, controller/trainer/schema revisions), its execution and its typed output manifest with file digests; a stage is reused only when that committed output still verifies through its consumer validator, failed or interrupted executions stay recorded and are retried into new directories, and a different request or changed source needs a new work root. `--attempt N` fits a new run from the pinned base; later resumes follow the highest attempt. The low-level commands below run the same stage implementations for diagnosis.

## Assets

```
semantic-trainer assets --model google/gemma-4-E2B-it --quant Q4_0
```

Builds or verifies, under `$XDG_CACHE_HOME/semantic-switch/trainer` (default `~/.cache/semantic-switch/trainer`, overridden by `SEMANTIC_TRAINER_ASSETS`):

- the HF snapshot at one commit (`--revision`, default: `main` resolved to its commit);
- llama.cpp at the pinned commit with `convert_hf_to_gguf.py`, `convert_lora_to_gguf.py`, `llama-export-lora` and `llama-quantize` (CPU build; needs git, cmake and a C++ compiler);
- the F16 GGUF converted from the snapshot and one quantized base per `--quant`.

Existing parts are reused; temporary files stay under the asset root. The receipt names the manifest digest. Jobs reference assets only through it, and every use re-verifies the recorded SHA-256 of each file. Export the native tune data with the pipeline-built quantized base so base and specialist differ only by the adapter.

## Labels

```
semantic-learn collect action.yaml situations.jsonl --teacher openrouter:google/gemma-4-31b-it --provider PROVIDER --training-use teacher-use.yaml --to labels.collection.json
ss label action.yaml LABELS.jsonl --to reviewed.jsonl --actor human
ss export action.yaml --native --labels reviewed.jsonl --task-family maintenance:alarms
```

Situation and label files are one versioned envelope: `{"schema": 3, "input": …, "groups": […], "pairs": […], "role": …, "tags": […], "selections": […]}`; a labelled situation adds `facts`, `revs` and `label_sources` with the same fact/member nesting as `facts`. Each target carries an ordered history of sources: `derivation` (`computed` with the procedure `revision`, `judged` with the observed producer route, `authored` with its `actor`, or `unknown`), producer, artifact digest, record/target address, appended `verifications` (verifier, actor, method, criterion revision, verified-content digest, confirm/replace/skip outcome) and, on a judged source only, its training use declaration. Raw domain lines and unversioned envelopes are rejected with re-encode guidance.

Teacher acquisition belongs to the optional `semantic-learn` package (`packages/semantic-learn`); the trainer has no collection command. `semantic-learn collect` decodes and validates the whole source before any teacher request, freezes the task, target meanings, source digest, teacher and code identity in `labels.journal.jsonl`, scores windows of 32 situations through public judgments and commits one record per situation. Every declared target (each scalar fact and each membership) gets a settled teacher answer or an explicit outcome: unexamined (a budgeted Select), missing, failed, rule, unstated, uncertain or returned-model drift. A rerun resumes uncommitted situations only; `--retry-failed` repeats transport failures as new attempts. The manifest publishes immutable `labels.<digest>.jsonl` (canonical envelopes, synthetic sources naming the teacher) and `unresolved.<digest>.jsonl` generations, the reconciled counts, request counts and journal/source bytes; the result names the label file to review. `--training-use` is the explicit training use declaration (`permission`, `model`, `provider`, `contract`, `revision`, `use`) of the teacher route: only `allowed` produces labels, an unknown or forbidden declaration and the core restriction table (Jev, `typesafe/jev-*`, is refused whatever is declared) fail before any request, and every settled label's observed producer route (returned `model@provider`, or the requested teacher when none is reported) must equal the declared route. Each judged label source (producer = the observed route) and the collection journal and manifest carry the declaration; Apache-licensed weights alone do not authorize a hosted service use. `prepare` rechecks every fit, model_select and acceptance_fit observation's full label history through the core `trainable` operation, so fitting without `semantic-learn` installed cannot admit forbidden teacher labels: any source from a restricted producer (including a verified or replaced one) is refused, and a judged source must carry an `allowed` declaration for exactly its producer route; computed and authored labels need no provider declaration, and a verification never substitutes for a permission. `ss label --actor …` appends a `review` verification to the supplied source, appends an authored decision naming the replaced value, and records skips in `<destination>.reviews.jsonl`. Export with the pipeline-built base so base and specialist differ only by the merged delta; the native export's `--task-family` is the source's task identity.

Exports carry a source-situation index (situation IDs over the full public input and task meanings, every target linked to its observation or an explicit exact/missing/unlabelled outcome, gold-completeness) and one `export_id` over the header, index and row digests; moving a manifest with its payload keeps the identity, any header or row change does not.

## Job

```
semantic-trainer prepare action.yaml action.export.jsonl.manifest.json --assets DIGEST --quant Q4_0 --device xpu:0 --native-device gpu \
    --recipe eval_every_examples=550 --recipe selection_unit=complete_situation --budget max_seconds=18000 --profile profiles/alarms.json --to jobs/alarms-1
```

Native settings start from the core `Model` defaults (`max_input_tokens` 1024, `max_prefix_tokens` 1024 covering chat template plus guidance, the fixed 1536-token question suffix including framing, and `n_ctx` normalized to their 3584-token sum), then apply the job's explicit native settings once. Before any native load, every exported presentation of every consumed role is checked segment by segment and in total against those caps; an oversized prefix, input, question or request names its task, target, observation and stage and fails without truncation. The HF `max_sequence_tokens` budget is a separate fitting quantity and never sets a native quota.

`prepare` and `resolve` share one cohort resolver. It validates and loads each distinct export (by `export_id`) once, keeps every occurrence of a repeated observation as a provenance record (export, namespace, source component, group aliases, family seeds), joins the globally comparable `key`, `observation`, `rendered` and `situation` seeds through `FamilyIndex` together with an anchor scoped to each export's source component, and only then deduplicates numerical rows. Raw group or pair aliases never join exports. Each canonical family's ID is the digest of its sorted shared seeds and the family-resolution revision; the resolved row's `component` is that family and its `family_seeds` the complete shared closure, so populations, monitoring, compatibility, native selection and the receipt all count canonical families (source components are reported as provenance counts). Repeated observations must agree on meaning, labels, evidence and native presentations. Roles come from the dataset assignment (tune folds 0–2 fit, 3 model_select, 4 acceptance_fit; acceptance_fit only with `--acceptance-fit`, otherwise the deployment keeps the authored, uncalibrated policy; check families are never exported for fitting) and are validated per canonical family before any budget: a family spanning two roles, even through an unused bridge, is refused with its source components and connecting seeds. `--fit-situations N` keeps whole canonical fit families whose union of situation IDs totals exactly N, or refuses. Unselected observations stay in the cohort as connectivity bridges, and the job lists every requested export, including connectivity-only ones. `--recipe KEY=VALUE` and `--budget KEY=VALUE` are the only recipe/budget setters: each key once, unknown keys refused, values typed by the field (lists as YAML); the job keeps the given overrides and the resolved job records them beside the resolved defaults. `prepare` validates everything (nonempty fit and model_select populations, disjoint nonempty in-vocabulary answer groups with an existing gold group, objective-aware support, budgets) before writing `job.yaml`; support for specialization needs fit support for every evaluated meaning, and instruction_transfer reports held-out meanings without it and keeps fit task families out of other roles. `prepare` freezes each task once through the core `semantic_switch.training.freeze_task` into `<job>/tasks/<contract>/`: the compiled definition with its resolved guidance texts (`task.yaml`, `guidance/*.txt`), the effective exact corrections chosen by the normal collection semantics from authored examples and the definition's `.examples.jsonl` sidecar (`task.examples.jsonl`, empty when there are none) and `frozen-task.json` (file digests, definition and guidance digests, per-target meaning revision and guidance digest, `exact_override`, the active override population with label-source digests and family seeds, and the `behavior` digest over all of it). Later edits to the source definition, its guidance files or its sidecar never reach the job; `resolve`, fitting and selection verify the bundle against the recorded behavior digest and refuse a changed bundle (prepare a new job). The original files may be moved or deleted. Every exported target must match the frozen meaning revision and guidance digest. Active overrides (none under `exact_override: false`) join the cohort's canonical families by their seeds; an override for an exported observation must agree with its label. Target meanings are compared through `semantic_switch.training.describe_task`. Populations report situations, complete situations, targets, observations, presentations, canonical families and source components per role. The job:

```yaml
schema: 8
loss: {name: full_vocabulary_group_nll, version: 2, reduction: float32, expression: ...}
objective: specialization
tasks: {<contract>: {source: /abs/action.yaml, bundle: tasks/<contract>, weight: 1}}
initialization: fresh
assets: {manifest: <digest from the receipt>, quant: Q4_0}
fitting: {device: xpu:0}
native: {device: gpu}
exports:
  - {path: action.export.jsonl.manifest.json, export_id: <digest>, task: <contract>, roles: {fit: [...], model_select: [...]}}
  - {path: bridge.export.jsonl.manifest.json, export_id: <digest>, task: <contract>, roles: {}}
selection: {fit_situations: 100, families: [...], situation_ids: [...]}
recipe: {eval_every_examples: 550, selection_unit: complete_situation}
budget: {max_seconds: 18000}
```

`tasks` is one nonempty map keyed by each frozen task contract (the `behavior` digest of `tasks/<contract>/frozen-task.json`); a single-task job is the same map with one entry. Every export names its contract and every row resolves against that task's frozen catalogue; observations, support, per-class counts and situation IDs (`<contract>:<situation>`) are scoped by contract, an observation or export repeated under two contracts is refused, and family closure stays global, so a shared input bridges tasks. Objective weights (`objective_weights`, reduction revision 2): per role the declared task weights (equal by default) are normalized to one, each split equally over the task's examples (situations; a situation-less authored observation is its own example) and each example share equally over its observations, then uniform over stages and over presentations within a stage. Row weights are scaled by the role's observation count, enter the fit and monitor identities, and drive both the update average and the monitored model_select NLL; task totals and example/observation/presentation/token counts are reported, and the run records consumed tokens per task. Ranking (HF retention and native selection) uses the macro mean over model_select task contracts of the per-task correct fraction in the declared unit, then the existing tie-breaks; pooled counts are still reported. `prepare --mixture MANIFEST` validates a frozen task mixture (`semantic_trainer.mixture`, schema 1: claim, per-family role adaptation/model_select/evaluation, contract and meaning revisions, exports, scoped label mappings, dataset/licence evidence with underlying datasets and permitted uses, quotas of at most 500 complete examples, adaptation weights; global family closure must not bridge roles and no dataset content feeds two roles) and prepares one `instruction_transfer` job over its adaptation and model_select tasks; evaluation tasks never enter the job. Each export is declared once; quotas and the 2,000-example adaptation cap count the canonical union of complete examples per task across its exports (shared examples once, no truncation), and coverage reports complete/incomplete examples, observations, families, presentations and tokens per task and role, independent of export partition or order. The prepared bundle holds `mixture/manifest.json`, the permission evidence by digest and `mixture/audit.json` (contract, coverage, original locators); resolution re-verifies them and current permissions without the original files. The audit identity enters the job identity but not the fit or monitor identities, so a claim or permission-record change needs a new preparation while numerical identities stay equal. Application selection publishes one task only: a multi-task run's candidates are initializers, ranked by `select JOB --run RUN --purpose initializer`. It converts base and shortlist like application selection, scores each model_select task under its own frozen definition, guidance and binding, ranks by the task-macro unit, records per-task counts, regressions, HF/native agreement, probabilities and work, and publishes `RUN/initializer-selection/record.json` (fitted proof, chosen PEFT content, native representation, mixture audit, plan, metrics, inherited memberships), never a lock. A run selected under a job differing only in its mixture audit keeps its original fitted record; the record binds the new audit.

`initialization` is `fresh`, `{selection}` (`prepare --init-selection RECORD`: the candidate chosen by an initializer-selection record, verified against the run's fitted proof, candidate digests and inherited memberships; a record that chose base is refused) or `{run, candidate}` (`prepare --init-run RUN --init-candidate NAME`, disclosed as experimental input without selection evidence): a retained candidate of a ready current-schema run, verified like selection (fitted-record proof, configuration and weight digests, shapes), on the same HF base content and native base digest with the same rank, alpha, dropout and target modules. Fitting loads it with `peft.PeftModel.from_pretrained(..., is_trainable=True)` as the only adapter over a frozen base, rechecks its digests, and optimizes those parameters with a new optimizer; point zero evaluates and saves the initializer, and every candidate is one delta relative to the original base. Its content, configuration, PEFT version and precision and its inherited memberships (adaptation, selection and acceptance_fit rows, transitively, marked `inherited`; corrections as identity) enter the fit identity; inherited family seeds join the cohort before role assignment, and a family that trained the initializer may only hold fit observations. Selection of a warm-started run ranks the zero (initializer) candidate as a finalist, checks the toolchain with the root fresh run's zero adapter, and publishes inherited rows in the receipt provenance as model-wide lineage, so they disqualify overlapping check evidence without adding per-target lock membership. The receipt also records the initialization kind, its evidence (initializer-selection record and mixture audit, or the experimental disclosure), candidate step, fitted identities and adapter digests.

`resolve` re-reads every export through the same resolver, refuses a changed `export_id`, resolves the group selectors against the complete cohort and refuses fit observations that no longer cover exactly the frozen `selection` families and situations. The resolved job (schema 11) records the frozen task, the correction population (`corrections`), the cohort (family-resolution revision, observation and family counts, digest of sorted memberships), `fit` and `monitor`. Both identities (revision 2) are built from one canonical numerical-observation description consumed by the trainer: observation ID, kind, classes and gold label, presentation weights and, per ordered presentation, stage, variant, prefix/input/question tokens, answer groups, gold group, slot map and global label; plus the tokenizer descriptor digest and the staged-answer/reduction revision. `fit` adds the base repository, revision and the sorted logical HF file names with content hashes from the verified asset manifest (no installation roots or conversion binaries), loss and objective, the ordered fit observations, adapter, optimizer, schedule, seed/order algorithm, placement and fitting implementation revision. `monitor` adds the ordered model_select and probe observation descriptions as the monitor consumes them, complete-situation composition (targets and completeness, not acquisition record histories), cadence, point count, unit, ranking, loss and stopping plan; identical observation IDs with other presentations are another monitoring computation. The envelope `id` (job_id) also covers provenance but not the bundle location; `fit.id` names only the values that determine the weights, and a matching identity is evidence of matching inputs, not of bitwise-deterministic execution. The fitted run's `resolved-job.json` records the actual Python, torch, transformers, PEFT, safetensors and trainer versions, the model type/device profile and `adapter`, the complete effective vanilla-LoRA configuration taken from the fitted PEFT configuration at publication (serialization defaults are expanded only there, from the documented profile of the installed PEFT version; supported: 0.21).

`fitting`: `device` (`cpu`, `xpu:N`, `cuda:N`), `precision` (bf16 on xpu/cuda; float32 default or bfloat16 on cpu), `threads` (default: physical cores), `attention` (`eager` default, `sdpa`), `gradient_checkpointing` (default off) and `fused_optimizer` (default off; the fused AdamW kernel). Reading or selecting a job decodes these settings without importing torch; fit and profile check the device against the installed torch once, immediately before model construction, with no fallback, and native selection checks its own requested llama.cpp device. `sdpa` and `fused_optimizer` are measured options: profile a job with them before adopting them. On `xpu` and `cuda`, Gemma 4's per-layer embedding table (4.4 GiB on E2B, a lookup) stays in host memory and the rest of the model is placed on the device; on integrated GPUs device memory is host memory that a systemd `MemoryMax` does not bound, so the model-job admission is the guard.

The loss is the full-vocabulary group NLL `softplus(logsumexp(z[not G]) - logsumexp(z[G]))` for gold answer group `G`, reduced in float32 from padded per-group answer coordinates prepared once per presentation: group log-sum-exps are gathered sparsely and the gold complement uses the largest non-gold logit (top-k excluding the gold group) as its stable shift, so no vocabulary-sized membership mask or complement copy is built. The forward runs the PEFT text trunk once, gathers the last real hidden state of each row and projects only those `[rows, hidden]` states through the head (Gemma final-logit softcapping applied); conditional answer loss and answer mass `exp(logsumexp(z[U]) - logsumexp(z))` are diagnostics. Nonfinite model outputs fail the run with a recorded `numerical_failure`. The loss identity is versioned in the job, progress, candidates and run manifests; jobs or runs under another identity are refused (prepare a new job and refit).

`recipe` defaults: all seven projections, rank 16, alpha 32, dropout 0, learning rate 2e-4, `constant` (or `cosine`) schedule, AdamW weight decay 0.01, gradient clip 1, batch 8 observations accumulated over padded forwards of `microbatch` presentations (default 1), an 8-epoch cap, `min_epochs` 2, `patience_examples` (default the fit observation count), relative `min_improvement` 0.001 and `selection_unit` `observation` or `complete_situation`. `eval_every_examples` has no default: a job without it is a population for profiling, and fitting needs the cadence chosen explicitly. Default warmup is independent of the cap: `warmup_examples = ceil_div(3 * fit_observations, 20)` (reference 3 epochs, fraction 1/20), resolved to steps under the batch size; `--recipe warmup_examples=N` is the only override and warmup beyond the available steps is refused. The constant schedule's learning rates for shared steps do not depend on the cap; cosine records its cap-dependent decay horizon. Examples seen count exported target observations consumed by completed optimizer steps. The resolved job fixes `max_optimizer_steps` (partial final batches included), the warmup policy, the exact maximum evaluation-point count (point zero and the forced final point counted once) and token work, and refuses budgets it would exceed; a changed task definition or export invalidates the job. `budget.feasibility_updates` (default 8) is the number K of optimizer updates timed for the in-run feasibility check.

## Fit

```
semantic-trainer lora jobs/alarms-1/job.yaml --to jobs/alarms-1/run --dry-run
systemd-run --user --scope -q -p MemoryMax=22G -p MemorySwapMax=0 semantic-trainer lora jobs/alarms-1/job.yaml --to jobs/alarms-1/run
semantic-trainer profile jobs/alarms-0/job.yaml --to profiles/alarms.json --steps 3 --warmup 1 --cadence 256 --cadence 550
```

One model job runs per host. The run directory exists from the start with `run.json` (`fitting`, then `ready` or `failed`). Point zero and every completed step crossing the examples-seen cadence evaluate the model_select rows (weighted NLL, raw correctness in both units, per path/class counts) and the in-sample fit probe; each point is appended to `progress.jsonl` and printed to stderr, and the learning rate of every completed update goes to `updates.jsonl`. Evaluation runs under inference mode and restores training mode. Evaluation groups consecutive rows into windows of at most `microbatch × max_sequence_tokens` tokens, forwards each window's presentations in length-sorted padded batches under the same bound, and moves one compact block (weighted NLL, answer mass, finiteness and conditional answer log-probabilities) to the host per window. Each point reserves its token work before it starts, polls the deadline at window boundaries and charges each completed window; an interrupted point appends an `interrupted_evaluation` record with reserved and charged tokens and is never ranked. The monitor owns a run-local work record (completed updates, points and checkpoint saves, training and monitor tokens, measured update/point/checkpoint durations), incremented only after each operation completes. After the first K updates the run projects `elapsed + remaining updates × mean update + remaining points × mean point + remaining checkpoint allowance × mean save`, where remaining work is the frozen plan minus completed counters at that boundary (point zero and earlier points are already in elapsed, a due point not yet started is pending, one save allowance per remaining nonzero point although retention can save fewer); it appends the `feasibility` record (elapsed, completed and remaining work, measured durations, assumptions) to `progress.jsonl` and `run.json`, and a projection beyond `max_seconds` or the token ceilings fails the run before further fitting. `max_seconds` is compute-run time from job resolution through tokenizer/config loading, admission, native baseline scoring, HF loading, updates, monitoring and checkpoint retention; the deadline is polled before each expensive stage and at its completion boundary, so it is cooperative, not a hard wall-clock limit, and publication time is reported separately. Expiry during a point leaves an unranked interrupted point; a point whose rows all completed after expiry is kept with `completed_after_deadline`, may take its one checkpoint, and stops the run on `time_budget`. Fitting stops on a loss plateau after the minimum epochs (`loss_plateau`), at the epoch cap (`epoch_cap`), or at a budget boundary (time exhaustion takes precedence over the cap or a plateau at the same boundary), keeping the fully evaluated points; the stop record separates trained and last-evaluated examples, unevaluated trailing updates, the best monitored point, the deadline (limit, elapsed, overrun, crossing operation, last complete point) and whether convergence was demonstrated (only a plateau whose best point is not at the last boundary). `candidates/` keeps the zero adapter and the two best evaluated points, staged and swapped in before eviction; the ranking rule (field order, NLL availability) is published with them and in the selection receipt; `candidates.json` (schema 8) carries `job_id`, `fit_id`, `monitor_id` and `fitted_job_id`, the canonical digest of the run's `resolved-job.json`, and lists them with the adapter weight and configuration digests and their HF predictions per observation (canonical answer and the answer at each presentation stage); `metrics.json` reports base HF/native agreement on the same presentations. A failed or nonfinite run keeps its diagnostics and no candidates. `profile` runs the fit's own update (loss, accumulation, clipping, optimizer, schedule) over the first `warmup + steps` fit batches and two complete monitor points (cold, steady: model_select plus the fit probe, checkpoint and progress I/O) on a disposable in-memory adapter of a prepared population (no cadence needed), synchronizing the device per phase: slot packing, collation, transfers, host embedding, forward, full-vocabulary reduction, window readout, backward, clip/optimizer, checkpoint and progress I/O, with inclusive `monitor:model_select` and `monitor:probe` totals. It reports tokens, presentations, observations, model loading time, resident and peak device bytes, peak host bytes, prepared-input bytes and device placement, and writes a new identified profile (schema 2) bound to the population and fit identities with the fitting configuration (assets, placement, loss, implementation, adapter, batching, sequence cap), the token workload, steady costs (update and point seconds per token, checkpoint seconds) and a projection per cadence (`--cadence`, default a quarter, half, one and two fit epochs): planned points, monitor tokens and total seconds against `max_seconds` and the token budgets. Native baseline scoring and early stopping are outside the projection. `prepare --profile` copies the profile into the job, refuses one measured under another fitting configuration, a token workload changed by more than half or a cadence it projects beyond the budgets, and records `cadence` (cadence, profile id, workload ratios and projection) in the resolved job; the profile is provenance of the cadence choice, not a monitoring input, so `monitor_id` is unchanged. Fitting resolves every fit and model_select presentation once after model loading into run-local CPU input records (token tensor, validated answer groups and gold, presentation weights), included in the admission envelope as `fit:prepared_inputs`, reused by every update and monitor point, reported in the stop record and released with the fitting stage; slot packing and padding stay per batch, and token tensors stay on the host so Gemma's host-resident per-layer table is gathered there and only the gathered inputs move to the device. The table is memory-mapped from the asset-verified safetensors snapshot through the cached tensor descriptor, without a reread comparison. Tokenizer vocabulary, probes and each unique answer token/text pair are checked once per tokenizer descriptor. Relative improvement requires `best_loss > 0` and `best_loss - loss > min_improvement × best_loss`; at a zero best loss no nonnegative loss improves.

## Deploy and select

```
systemd-run --user --scope -q -p MemoryMax=22G -p MemorySwapMax=0 semantic-trainer select jobs/alarms-1/job.yaml --run jobs/alarms-1/run
semantic-trainer check jobs/alarms-1/run/deployment/receipt.json check.jsonl --evidence check.dataset.json --to jobs/alarms-1/check
```

`select --representation` chooses the deployed form once, before native selection; policies, checks and the lock belong to that form, and changing it requires selecting again (the HF fit is unchanged). `runtime-adapter` converts each retained PEFT delta to an adapter GGUF with the pinned `convert_lora_to_gguf.py`, validates its rank, alpha and targets against the fitted recipe and the base, and scores base and shortlist on one resident pipeline-built quantized base under one model job whose estimate charges the base once and every adapter once (tensor bytes by type and placement plus the pinned allocation overhead, checked against the buffers llama.cpp reports); the deployment stages `base.gguf` and `adapter.gguf` with independent hashes and the lock pins the binding with `representation: runtime-adapter` and scale 1. That build's runtime-adapter capability remains unproven until the separately invoked `bench/adapter_profile.py` measures it.

A job prepared with `--scope FACT[/MEMBER]` adapts and selects only those targets under the binding they inherit; selection loads a trial view that rebinds exactly those targets (and their staged questions and Select members) to each candidate, so unrelated bindings, local or hosted, are never loaded or scored. Without `--binding`, `select` publishes scoped support: the receipt names its targets and binding, and `Runtime.load` refuses it as an application; install it by role, `Runtime(bindings={ROLE: ss.judge(DEPLOYMENT), ...}).load(APPLICATION)`. `select --binding ROLE=JUDGE` for every remaining role publishes a complete application whose lock pins those bindings, their execution and their authored policies; missing or extra roles fail before any conversion or model allocation. Scoped selection results are no claim about the complete application.

In the `merged` representation every candidate is deployed as one GGUF: `convert_lora_to_gguf.py --outtype f16`, `llama-export-lora` into the asset F16 base, `llama-quantize` to the job's type. Nothing is merged into a quantized base or requantized. The zero adapter must reproduce the pipeline-built quantized base byte for byte (measured for Gemma 4 E2B Q4_0 at the pinned toolchain: the merged F16 differs from the base F16 in bytes, the quantized file is identical), and converted tensors must be finite with the fitted shapes. In the `runtime-adapter` representation no candidate or zero adapter is merged or quantized: the zero proof reads the null adapter's `lora_B` factors through the cached safetensors descriptor and requires every one to be exactly zero, and the scored base must be the pipeline-built quantized base itself. Application and initializer selection share one admission, shortlist, conversion, trial and publication orchestration and differ only in what they publish.

Selection scores the model_select families through public addressed observation rows on each retained candidate and the base under one native configuration (a `gpu` request refuses CPU realization), and keeps the most raw-correct in the declared unit (complete situations are reconstructed through the source-situation index; a missing target makes the situation incorrect), then fewer path/class regressions against base, then the base, then the earlier step; selection requires the candidates' loss identity to equal the job's. HF/native agreement is a compatibility diagnostic, never a gate: per candidate, specialist HF/native agreement is compared with base (zero adapter) HF/native agreement on the same targets and stages, missing outputs counting as disagreements, with the family-paired difference, `unchanged`/`sparse`/`measured` status, no predeclared tolerance, and native fixes/regressions against gold on disagreeing targets. It includes backend and precision effects; quantization alone would need a measured same-backend F16-to-Q8 comparison, which is not recorded. It reports per-class predicted versus gold counts, per-family fixes and regressions, contrast-pair correctness and p50 public latency for every candidate; no significance gate. `selection_work` separates public judge-only scoring (whose per-observation latencies give `p50_ms`), the exported-presentation HF/native diagnostic pass and their total. Each trial's judge is constructed through `semantic_switch.training.Selection` with one stable score ledger bounded by the exported-presentation requests; the diagnostic pass reuses a public native score block only for a request identical in prefix, input, questions and answer slots under the same weight/adapter content and native execution identity. Failed, partial, nonfinite or reference-mode public rows are rescored, the ledger is released when the trial closes, and the reuse counters report requests, reused, scored and rows. Every trial records its own model identity and realized execution; trials under different non-weight settings are rejected. Acceptance is the authored policy with `calibration: absent` unless the job was prepared with `--acceptance-fit`; then thresholds are fitted once on those families of the selected model (in-sample diagnostics, never held-out evidence).

Native ranking uses only the judge source (`sources: ['judge']` in the selection report) on the frozen task and guidance; exact corrections and fitted acceptance policies are application behavior that the receipt identifies and the check evaluates. Selection keeps shortlist construction, conversion, native ranking and publication; the core `freeze_specialization` re-verifies the frozen bundle, requires the provenance `override` declarations to equal its active override population, validates acceptance addresses, meaning revisions, label classes and provenance, fits acceptance_fit policies, asserts the realized identity of the selected trial and freezes the task and lock into the caller's empty staging directory, inside the selection's model job. Selection stages `specialist.gguf`, the bundled `task.yaml` with its guidance files, `task.lock.json` (frozen policies, model identity and realized execution) and `receipt.json` (bundle digests, requested native settings, realized execution, selection report, acceptance status the `behavior` record (frozen behavior, definition, guidance, correction and override-population digests, override count) and the provenance rows tagged `adaptation`, `selection`, `acceptance_fit` and `override`; an override for an observation already declared merges its use and label sources, an override-only row has no export occurrences). The staged task and lock must reproduce the frozen behavior digest before publication, fsyncs them and renames the directory to `run/deployment` in one step; an interrupted selection publishes nothing. `ss.load(DEPLOYMENT)` or `Runtime().load(DEPLOYMENT)` (the directory, its `receipt.json` or a `current` pointer to it) loads the fitted lock, its model and its frozen task after the original task directory is gone, without the trainer or torch; another realized execution, an altered payload or a runtime binding another model to its role fails explicitly. `ss.judge(DEPLOYMENT)` (`semantic_switch.training.fitted`) is model-only and carries no task policy. Each published fitted lock is an immutable entry; `semantic_switch.training.point`/`rollback` move an atomic `current` pointer between verified locks. The base may remain selected; its choice still depends on the fitted rivals, which the provenance records.

`semantic-trainer check` counts override evidence in its overlap accounting whether a check decision uses the example or the judge, and reports an older deployment whose lock embeds active examples without `override` declarations as `undeclared_overrides` rather than disjoint. It loads the published deployment, appends the exposure record before scoring and publishes a separate report referencing the receipt, candidate, lock and execution; it never selects, calibrates or edits the deployment. External adapters are merged with the same commands before use.

## Candidate validation

Before model admission or conversion, `select` validates the run through one operation: `run.json`, `candidates.json` and `resolved-job.json` must be ready and of the current schemas (otherwise it names them and the exact `semantic-trainer lora JOB --to NEW_RUN` refit; an unsupported job requires `semantic-trainer prepare`), the loss identity must match, `fitted_job_id` must equal the canonical digest of the original `resolved-job.json` (a missing digest is missing proof; an edited record is reported as edited metadata, which alone does not establish changed weights, and restoring the authentic record restores eligibility), the run, candidate list and fitted record must name the same job, fit and monitor identities, the fitted fit/monitor field digests must equal the resolved job's (changed numerical inputs or a changed monitoring plan require a refit), the job identity must match and the fitted record must describe the resolved job. Then the base digest and every candidate's weights, configuration bytes and normalized configuration digest are checked. The shared adapter validator, used by publication and conversion, parses `adapter_config.json` against the recorded effective configuration and PEFT version, rejects variants (DoRA, LoRA bias, layer replication, aLoRA, PiSSA-style initializers, unknown settings) and per-module rank/alpha patterns, compares rank, alpha/scaling, dropout, targets, orientation, bias, modules-to-save and base revision with the recorded recipe and targets, and checks weight tensor names and shapes. Base paths and other provenance fields are not identity. There is no migration of earlier fitting or job schemas; old runs and exposure audits stay on disk unchanged.

### Monitoring and interruption

Monitoring uses `evaluation_batch_size` (default 1) and `max_padded_tokens`, independently of gradient `microbatch`. The default `fit_probe_observations=0` disables the in-sample fit probe; candidate ranking still evaluates the full model-select population. Points include actual forward counts, padded tokens and semantic permutation deltas from the same forwards.

Specialization does not profile by default. Its cadence defaults to one actual fit epoch plus zero/final boundaries. Explicit profiling uses a durable bounded timing sample, reports extrapolation and times complete operations; estimates never refuse a chosen cadence. Token-work ceilings are optional. The elapsed-time limit and representation/memory bounds remain effective.

Fits keep evaluated candidates on failure. Recovery stores trainable adapter weights, optimizer/scheduler state, RNG, counters and the next epoch/batch cursor. `semantic-trainer lora JOB --to RUN` retries that identified attempt; a different specialization `--attempt` starts fresh. `--checkpoint-seconds` changes the operational save interval, default 300 seconds, without changing the training objective. Incomplete checkpoint staging is never eligible. Evaluation resumes committed blocks under the same checkpoint and batch plan; only complete points enter ranking. Final publication can be retried without inference.

### Behavioral coverage and loss allocation

`objective_balance=class_family` is an explicit recipe option. The same planner preserves each task/target's current total effort, divides it over supported classes and their canonical families, and retains relative row shares inside each family/class cell. Stage and permutation weights remain normalized. The default `situation` allocation is unchanged. Selection data is never rebalanced. The population records before/after effort and maximum row multiplier; absent classes are reported rather than refusing a diagnostic fit.

Authored slices use published tags, not predictions:

```yaml
recipe:
  objective_balance: class_family
  behavior_slices:
    - name: calibration
      tags: ["prompt:calibration_1"]
  development_recall:
    - target: method_inconsistent
      class: "true"
      slice: calibration
      minimum: 0.8
```

A slice can use `tags` (all required) and `any_tags` (at least one required). A requirement can name a `task` contract when target names overlap. The floor above is an example application requirement, not a default. Support reports include empty declared cells and overlapping slices without multiplying their training weights. Class/family balance does not balance every context inside a class.

Development requirements prefer qualifying checkpoints before the bounded retention shortlist is pruned, then use the normal aggregate ranking. If none qualifies, the ordinary best candidate remains available with its failures reported. HF floors measure raw semantic recall; native comparison/adoption separately measures operational recall, including withholding. Nothing automatically extends training, generates data or promotes a model.

### Recipe qualification and fit diagnosis

```bash
semantic-trainer qualify JOB.yaml --to QUALIFICATION
semantic-trainer qualify JOB.yaml --to QUALIFICATION --run
semantic-trainer diagnose JOB.yaml --target ready_to_print --class true --families 4 --to DIAGNOSTIC
semantic-trainer diagnose JOB.yaml --target ready_to_print --class true --families 4 --to DIAGNOSTIC --run
```

Qualification declares all five jobs before execution: seeds 0/1/2 at nominal LR, then seed 0 at half/twice LR. It uses existing fitting, recovery and native selection and resumes matching completed work. Reports retain failures and incomplete states, curves and worst/median/range of development results. This is explicitly invoked; ordinary specialization still runs once. Public Python entry points are lazy `semantic_trainer.qualify` and `semantic_trainer.diagnose`.

Fit diagnosis closes an explicit small fit-family cohort, verifies canonical slot/class alignment and contradictory labels, and enables the existing in-sample probe. A bounded separate selection family remains selection-only. Probe class counts and probability diagnostics reuse its forwards. `--rank 64` changes ordinary LoRA rank while preserving alpha and the existing merge/GGUF path. Memorization does not establish held-out quality or a backbone capacity limit.

A completed matching nominal fit can be reused with `qualify ... --nominal-run RUN --nominal-receipt RECEIPT`; omit the receipt option when it is at `RUN/deployment/receipt.json`. Reuse verifies the numerical fit/monitor identities and native configuration, references the existing weights and curves, and performs no inference or copying. Qualification reports differing measured environments as incomparable.
