# semantic-trainer

Optional fitting package for semantic-switch: lexical heads, probes and task-specific LoRA on the default student. The runtime package never depends on it or on torch.

## Install

The trainer runs in its own environment. Install the torch wheel that matches the fitting device first, then the package; an already installed torch is kept.

| Device | Install |
| --- | --- |
| CPU | `python -m venv .venv-cpu && .venv-cpu/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu` |
| Intel XPU (Arc, Panther Lake) | `python -m venv .venv-xpu && .venv-xpu/bin/pip install torch --index-url https://download.pytorch.org/whl/xpu` |
| NVIDIA CUDA | `python -m venv .venv-cuda && .venv-cuda/bin/pip install torch --index-url https://download.pytorch.org/whl/cu128` (pick the CUDA index matching the driver) |

Then, from the repository root: `<env>/bin/pip install -e '.[local]' -e 'packages/semantic-trainer[lora]'`. Lexical heads only need `semantic-trainer[lexical]`.

Check the device: `<env>/bin/python -c "import torch; print(torch.__version__, torch.xpu.is_available(), torch.cuda.is_available())"`.

## Core contract

The trainer (Python ≥ 3.12, `semantic-switch>=0.26,<0.27`) integrates through immutable files and supported in-process operations: `semantic_switch.training.describe_task` (integration revision, switch revision, input fields, observed targets by full address with meaning revision, answers, evidence reads and policy) and `Task` (task-bound situation normalization, input keys and label records for collection); native exports (`read_export`), `FamilyIndex` seed closure, `LabelSource` records, the leased `Journal`, `Runtime`/`Switch` public scoring and `score_observations`; `semantic_switch.tools.freeze_specialization` (revisioned result: task/guidance/lock hashes, lock id and candidate id, realized identity, acceptance summary) and `load_receipt`. It never traverses compiled plans or snapshots, constructs internal examples or assembles locks. Model execution stays in core; no application runtime imports the trainer.

## Assets

```
semantic-trainer assets --model google/gemma-4-E2B-it --quant Q4_0
```

Builds or verifies, under `$XDG_CACHE_HOME/semantic-switch/trainer` (default `~/.cache/semantic-switch/trainer`, overridden by `SEMANTIC_TRAINER_ASSETS`):

- the HF snapshot at one commit (`--revision`, default: `main` resolved to its commit);
- llama.cpp at the pinned commit with `convert_hf_to_gguf.py`, `convert_lora_to_gguf.py`, `llama-export-lora` and `llama-quantize` (CPU build; needs git, cmake and a C++ compiler);
- the F16 GGUF converted from the snapshot and one quantized base per `--quant`.

Existing parts are reused; temporary files stay under the asset root. The receipt names the manifest digest. Jobs reference assets only through it, and every use re-verifies the recorded SHA-256 of each file. Export the native tune data with the pipeline-built quantized base so base and specialist differ only by the adapter.

## Labels

```
semantic-trainer collect action.yaml situations.jsonl --teacher openrouter:google/gemma-4-31b-it --provider PROVIDER --to labels.collection.json
ss label action.yaml LABELS.jsonl --to reviewed.jsonl
ss export action.yaml --native --labels reviewed.jsonl --task-family maintenance:alarms
```

Situation and label files are one versioned envelope: `{"schema": 2, "input": …, "groups": […], "pairs": […], "role": …, "tags": […], "selections": […]}`; a labelled situation adds `facts`, `revs` and `label_sources` with the same fact/member nesting as `facts`. Each target carries an ordered history of sources (`origin` human, rule, synthetic or unknown; producer and its digest; artifact digest; record/target address; review entries with kind, reviewer, reviewed-content digest and confirm/replace/skip outcome). Raw domain lines and unversioned envelopes are rejected with re-encode guidance.

`collect` decodes and validates the whole source before any teacher request, freezes the task, target meanings, source digest, teacher and code identity in `labels.journal.jsonl`, scores windows of 32 situations through public judgments and commits one record per situation. Every declared target (each scalar fact and each membership) gets a settled teacher answer or an explicit outcome: unexamined (a budgeted Select), missing, failed, rule, unstated, uncertain or returned-model drift. A rerun resumes uncommitted situations only; `--retry-failed` repeats transport failures as new attempts. The manifest publishes immutable `labels.<digest>.jsonl` (canonical envelopes, synthetic sources naming the teacher) and `unresolved.<digest>.jsonl` generations, the reconciled counts, request counts and journal/source bytes; the result names the label file to review. Teachers must permit training use (Gemma 4 and Qwen 3.5/3.6 are Apache-2.0); Jev (`typesafe/jev-*`) is refused. `ss label` keeps confirmed producer labels with a review entry, appends a human decision naming the replaced value, and records skips in `<destination>.reviews.jsonl`. Export with the pipeline-built base so base and specialist differ only by the merged delta; the native export's `--task-family` is the source's task identity.

Exports carry a source-situation index (situation IDs over the full public input and task meanings, every target linked to its observation or an explicit exact/missing/unlabelled outcome, gold-completeness) and one `export_id` over the header, index and row digests; moving a manifest with its payload keeps the identity, any header or row change does not.

## Job

```
semantic-trainer prepare action.yaml action.export.jsonl.manifest.json --assets DIGEST --quant Q4_0 --device xpu:0 --native-device gpu \
    --recipe eval_every_examples=550 --recipe selection_unit=complete_situation --budget max_seconds=18000 --profile profiles/alarms.json --to jobs/alarms-1
```

`prepare` and `resolve` share one cohort resolver. It validates and loads each distinct export (by `export_id`) once, keeps every occurrence of a repeated observation as a provenance record (export, namespace, source component, group aliases, family seeds), joins the globally comparable `key`, `observation`, `rendered` and `situation` seeds through `FamilyIndex` together with an anchor scoped to each export's source component, and only then deduplicates numerical rows. Raw group or pair aliases never join exports. Each canonical family's ID is the digest of its sorted shared seeds and the family-resolution revision; the resolved row's `component` is that family and its `family_seeds` the complete shared closure, so populations, monitoring, compatibility, native selection and the receipt all count canonical families (source components are reported as provenance counts). Repeated observations must agree on meaning, labels, evidence and native presentations. Roles come from the dataset assignment (tune folds 0–2 fit, 3 model_select, 4 acceptance_fit; acceptance_fit only with `--acceptance-fit`, otherwise the deployment keeps the authored, uncalibrated policy; check families are never exported for fitting) and are validated per canonical family before any budget: a family spanning two roles, even through an unused bridge, is refused with its source components and connecting seeds. `--fit-situations N` keeps whole canonical fit families whose union of situation IDs totals exactly N, or refuses. Unselected observations stay in the cohort as connectivity bridges, and the job lists every requested export, including connectivity-only ones. `--recipe KEY=VALUE` and `--budget KEY=VALUE` are the only recipe/budget setters: each key once, unknown keys refused, values typed by the field (lists as YAML); the job keeps the given overrides and the resolved job records them beside the resolved defaults. `prepare` validates everything (nonempty fit and model_select populations, disjoint nonempty in-vocabulary answer groups with an existing gold group, objective-aware support, budgets) before writing `job.yaml`; support for specialization needs fit support for every evaluated meaning, and instruction_transfer reports held-out meanings without it and keeps fit task families out of other roles. `prepare` freezes the task once through the core `semantic_switch.training.freeze_task` into `<job>/task/`: the compiled definition with its resolved guidance texts (`task.yaml`, `guidance/*.txt`), the effective exact corrections chosen by the normal collection semantics from authored examples and the definition's `.examples.jsonl` sidecar (`task.examples.jsonl`, empty when there are none) and `frozen-task.json` (file digests, definition and guidance digests, per-target meaning revision and guidance digest, `exact_override`, the active override population with label-source digests and family seeds, and the `behavior` digest over all of it). Later edits to the source definition, its guidance files or its sidecar never reach the job; `resolve`, fitting and selection verify the bundle against the recorded behavior digest and refuse a changed bundle (prepare a new job). The original files may be moved or deleted. Every exported target must match the frozen meaning revision and guidance digest. Active overrides (none under `exact_override: false`) join the cohort's canonical families by their seeds; an override for an exported observation must agree with its label. Target meanings are compared through `semantic_switch.training.describe_task`. Populations report situations, complete situations, targets, observations, presentations, canonical families and source components per role. The job:

```yaml
schema: 7
loss: {name: full_vocabulary_group_nll, version: 2, reduction: float32, expression: ...}
objective: specialization
task: {source: /abs/action.yaml, bundle: task, behavior: <digest from task/frozen-task.json>}
assets: {manifest: <digest from the receipt>, quant: Q4_0}
fitting: {device: xpu:0}
native: {device: gpu}
exports:
  - {path: action.export.jsonl.manifest.json, export_id: <digest>, roles: {fit: [...], model_select: [...]}}
  - {path: bridge.export.jsonl.manifest.json, export_id: <digest>, roles: {}}
selection: {fit_situations: 100, families: [...], situation_ids: [...]}
recipe: {eval_every_examples: 550, selection_unit: complete_situation}
budget: {max_seconds: 18000}
```

`resolve` re-reads every export through the same resolver, refuses a changed `export_id`, resolves the group selectors against the complete cohort and refuses fit observations that no longer cover exactly the frozen `selection` families and situations. The resolved job (schema 8) records the frozen task, the correction population (`corrections`), the cohort (family-resolution revision, observation and family counts, digest of sorted memberships), `fit` and `monitor`. Both identities (revision 2) are built from one canonical numerical-observation description consumed by the trainer: observation ID, kind, classes and gold label, presentation weights and, per ordered presentation, stage, variant, prefix/input/question tokens, answer groups, gold group, slot map and global label; plus the tokenizer descriptor digest and the staged-answer/reduction revision. `fit` adds the base repository, revision and the sorted logical HF file names with content hashes from the verified asset manifest (no installation roots or conversion binaries), loss and objective, the ordered fit observations, adapter, optimizer, schedule, seed/order algorithm, placement and fitting implementation revision. `monitor` adds the ordered model_select and probe observation descriptions as the monitor consumes them, complete-situation composition (targets and completeness, not acquisition record histories), cadence, point count, unit, ranking, loss and stopping plan; identical observation IDs with other presentations are another monitoring computation. The envelope `id` (job_id) also covers provenance but not the bundle location; `fit.id` names only the values that determine the weights, and a matching identity is evidence of matching inputs, not of bitwise-deterministic execution. The fitted run's `resolved-job.json` records the actual Python, torch, transformers, PEFT, safetensors and trainer versions and the model type/device profile.

`fitting`: `device` (`cpu`, `xpu:N`, `cuda:N`; checked against the installed torch, no fallback), `precision` (bf16 on xpu/cuda; float32 default or bfloat16 on cpu), `threads` (default: physical cores), `attention` (`eager` default, `sdpa`), `gradient_checkpointing` (default off). On `xpu` and `cuda`, Gemma 4's per-layer embedding table (4.4 GiB on E2B, a lookup) stays in host memory and the rest of the model is placed on the device; on integrated GPUs device memory is host memory that a systemd `MemoryMax` does not bound, so the model-job admission is the guard.

The loss is the full-vocabulary group NLL `softplus(logsumexp(z[not G]) - logsumexp(z[G]))` for gold answer group `G`, reduced in float32 from unique unpadded token-membership coordinates built on the host; conditional answer loss and answer mass `exp(logsumexp(z[U]) - logsumexp(z))` are diagnostics. Nonfinite model outputs fail the run with a recorded `numerical_failure`. The loss identity is versioned in the job, progress, candidates and run manifests; jobs or runs under another identity are refused (prepare a new job and refit).

`recipe` defaults: all seven projections, rank 16, alpha 32, dropout 0, learning rate 2e-4, `constant` (or `cosine`) schedule, AdamW weight decay 0.01, gradient clip 1, batch 8 observations accumulated over padded forwards of `microbatch` presentations (default 1), an 8-epoch cap, `min_epochs` 2, `patience_examples` (default the fit observation count), relative `min_improvement` 0.001 and `selection_unit` `observation` or `complete_situation`. `eval_every_examples` has no default: choose the cadence explicitly. Default warmup is independent of the cap: `warmup_examples = ceil_div(3 * fit_observations, 20)` (reference 3 epochs, fraction 1/20), resolved to steps under the batch size; `--recipe warmup_examples=N` is the only override and warmup beyond the available steps is refused. The constant schedule's learning rates for shared steps do not depend on the cap; cosine records its cap-dependent decay horizon. Examples seen count exported target observations consumed by completed optimizer steps. The resolved job fixes `max_optimizer_steps` (partial final batches included), the warmup policy, the exact maximum evaluation-point count (point zero and the forced final point counted once) and token work, and refuses budgets it would exceed; a changed task definition or export invalidates the job. `budget.feasibility_updates` (default 8) is the number K of optimizer updates timed for the in-run feasibility check.

## Fit

```
semantic-trainer lora jobs/alarms-1/job.yaml --to jobs/alarms-1/run --dry-run
systemd-run --user --scope -q -p MemoryMax=22G -p MemorySwapMax=0 semantic-trainer lora jobs/alarms-1/job.yaml --to jobs/alarms-1/run
semantic-trainer profile jobs/alarms-0/job.yaml --to profiles/alarms.json --steps 3 --warmup 1 --cadence 256 --cadence 550
```

One model job runs per host. The run directory exists from the start with `run.json` (`fitting`, then `ready` or `failed`). Point zero and every completed step crossing the examples-seen cadence evaluate the model_select rows (weighted NLL, raw correctness in both units, per path/class counts) and the in-sample fit probe; each point is appended to `progress.jsonl` and printed to stderr, and the learning rate of every completed update goes to `updates.jsonl`. Evaluation runs under inference mode and restores training mode. Each point reserves its token work before it starts and charges completed rows as they finish; an interrupted point appends an `interrupted_evaluation` record with reserved and charged tokens and is never ranked. The monitor owns a run-local work record (completed updates, points and checkpoint saves, training and monitor tokens, measured update/point/checkpoint durations), incremented only after each operation completes. After the first K updates the run projects `elapsed + remaining updates × mean update + remaining points × mean point + remaining checkpoint allowance × mean save`, where remaining work is the frozen plan minus completed counters at that boundary (point zero and earlier points are already in elapsed, a due point not yet started is pending, one save allowance per remaining nonzero point although retention can save fewer); it appends the `feasibility` record (elapsed, completed and remaining work, measured durations, assumptions) to `progress.jsonl` and `run.json`, and a projection beyond `max_seconds` or the token ceilings fails the run before further fitting. `max_seconds` is compute-run time from job resolution through tokenizer/config loading, admission, native baseline scoring, HF loading, updates, monitoring and checkpoint retention; the deadline is polled before each expensive stage and at its completion boundary, so it is cooperative, not a hard wall-clock limit, and publication time is reported separately. Expiry during a point leaves an unranked interrupted point; a point whose rows all completed after expiry is kept with `completed_after_deadline`, may take its one checkpoint, and stops the run on `time_budget`. Fitting stops on a loss plateau after the minimum epochs (`loss_plateau`), at the epoch cap (`epoch_cap`), or at a budget boundary (time exhaustion takes precedence over the cap or a plateau at the same boundary), keeping the fully evaluated points; the stop record separates trained and last-evaluated examples, unevaluated trailing updates, the best monitored point, the deadline (limit, elapsed, overrun, crossing operation, last complete point) and whether convergence was demonstrated (only a plateau whose best point is not at the last boundary). `candidates/` keeps the zero adapter and the two best evaluated points, staged and swapped in before eviction; the ranking rule (field order, NLL availability) is published with them and in the selection receipt; `candidates.json` (schema 6) carries `job_id`, `fit_id` and `monitor_id` and lists them with the adapter weight and configuration digests and their HF predictions per observation (canonical answer and the answer at each presentation stage); `metrics.json` reports base HF/native agreement on the same presentations. A failed or nonfinite run keeps its diagnostics and no candidates. `profile` runs the fit's own update (loss, accumulation, clipping, optimizer, schedule) over the first `warmup + steps` fit batches and two complete monitor points (cold, steady: model_select plus the fit probe, checkpoint and progress I/O) on a disposable in-memory adapter of a prepared (possibly provisional) job, synchronizing the device per phase: slot packing, collation, transfers, host embedding, forward, full-vocabulary reduction, backward, clip/optimizer, checkpoint and progress I/O, with inclusive `monitor:model_select` and `monitor:probe` totals. It reports tokens, presentations, observations, model loading time, resident and peak device bytes, peak host bytes, prepared-input bytes and device placement, and writes a new identified profile (schema 1) with the fitting configuration (assets, placement, loss, implementation, adapter, batching, sequence cap), the token workload, steady costs (update and point seconds per token, checkpoint seconds) and a projection per cadence (`--cadence`, default a quarter, half, one and two fit epochs plus the job's own): planned points, monitor tokens and total seconds against `max_seconds` and the token budgets. Native baseline scoring and early stopping are outside the projection. `prepare --profile` copies the profile into the job, refuses one measured under another fitting configuration, a token workload changed by more than half or a cadence it projects beyond the budgets, and records `cadence` (cadence, profile id, workload ratios and projection) in the resolved job; the profile is provenance of the cadence choice, not a monitoring input, so `monitor_id` is unchanged. Fitting resolves every fit and model_select presentation once after model loading into run-local CPU input records (token tensor, validated answer groups and gold, presentation weights), included in the admission envelope as `fit:prepared_inputs`, reused by every update and monitor point, reported in the stop record and released with the fitting stage; slot packing and padding stay per batch.

## Deploy and select

```
systemd-run --user --scope -q -p MemoryMax=22G -p MemorySwapMax=0 semantic-trainer select jobs/alarms-1/job.yaml --run jobs/alarms-1/run
semantic-trainer check jobs/alarms-1/run/deployment/receipt.json check.jsonl --evidence check.dataset.json --to jobs/alarms-1/check
```

Every candidate is deployed as one GGUF: `convert_lora_to_gguf.py --outtype f16`, `llama-export-lora` into the asset F16 base, `llama-quantize` to the job's type. Nothing is merged into a quantized base or requantized. The zero adapter must reproduce the pipeline-built quantized base byte for byte (measured for Gemma 4 E2B Q4_0 at the pinned toolchain: the merged F16 differs from the base F16 in bytes, the quantized file is identical), and converted tensors must be finite with the fitted shapes.

Selection scores the model_select families through public addressed observation rows on each retained candidate and the base under one native configuration (a `gpu` request refuses CPU realization), and keeps the most raw-correct in the declared unit (complete situations are reconstructed through the source-situation index; a missing target makes the situation incorrect), then fewer path/class regressions against base, then the base, then the earlier step; selection requires the candidates' loss identity to equal the job's. HF/native agreement is a compatibility diagnostic, never a gate: per candidate, specialist HF/native agreement is compared with base (zero adapter) HF/native agreement on the same targets and stages, missing outputs counting as disagreements, with the family-paired difference, `unchanged`/`sparse`/`measured` status, no predeclared tolerance, and native fixes/regressions against gold on disagreeing targets. It includes backend and precision effects; quantization alone would need a measured same-backend F16-to-Q8 comparison, which is not recorded. It reports per-class predicted versus gold counts, per-family fixes and regressions, contrast-pair correctness and p50 public latency for every candidate; no significance gate. `selection_work` separates public judge-only scoring (whose per-observation latencies give `p50_ms`), the exported-presentation HF/native diagnostic pass and their total. The diagnostic pass reuses a public native score block only for a token request identical in prefix, input, questions and answer groups under the same runtime (`Runtime.recording`); failed or nonfinite public rows are rescored, and the reuse counters report requests, reused, scored and rows. Every trial records its own model identity and realized execution; trials under different non-weight settings are rejected. Acceptance is the authored policy with `calibration: absent` unless the job was prepared with `--acceptance-fit`; then thresholds are fitted once on those families of the selected model (in-sample diagnostics, never held-out evidence).

Native ranking uses only the judge source (`sources: ['judge']` in the selection report) on the frozen task and guidance; exact corrections and fitted acceptance policies are application behavior that the receipt identifies and the check evaluates. Selection keeps shortlist construction, conversion, native ranking and publication; the core `semantic_switch.tools.freeze_specialization` re-verifies the frozen bundle, requires the provenance `override` declarations to equal its active override population, validates acceptance addresses, meaning revisions, label classes and provenance, fits acceptance_fit policies, asserts the realized identity of the selected trial and freezes the task and lock into the caller's empty staging directory, inside the selection's model job. Selection stages `specialist.gguf`, the bundled `task.yaml` with its guidance files, `task.lock.json` (frozen policies, model identity and realized execution) and `receipt.json` (bundle digests, requested native settings, realized execution, selection report, acceptance status the `behavior` record (frozen behavior, definition, guidance, correction and override-population digests, override count) and the provenance rows tagged `adaptation`, `selection`, `acceptance_fit` and `override`; an override for an observation already declared merges its use and label sources, an override-only row has no export occurrences). The staged task and lock must reproduce the frozen behavior digest before publication, fsyncs them and renames the directory to `run/deployment` in one step; an interrupted selection publishes nothing. `Runtime.from_specialization(receipt)` loads the evaluated binding and `runtime.load()` its frozen task after the original task directory is gone; another realized execution fails explicitly. `Model.from_specialization(receipt)` is model-only and carries no task policy. The base may remain selected; its choice still depends on the fitted rivals, which the provenance records.

`semantic-trainer check` counts override evidence in its overlap accounting whether a check decision uses the example or the judge, and reports an older deployment whose lock embeds active examples without `override` declarations as `undeclared_overrides` rather than disjoint. It loads the published deployment, appends the exposure record before scoring and publishes a separate report referencing the receipt, candidate, lock and execution; it never selects, calibrates or edits the deployment. External adapters are merged with the same commands before use.

## Migrating a preceding run

```
semantic-trainer prepare ... --to jobs/alarms-2
semantic-trainer migrate jobs/alarms-2/job.yaml --run jobs/alarms-1/run --to jobs/alarms-2/compatibility.json
semantic-trainer select jobs/alarms-2/job.yaml --run jobs/alarms-1/run --compatibility jobs/alarms-2/compatibility.json
```

`migrate` reads only a ready run of the immediately preceding loss-v2 schemas (resolved job 7, candidates 5, run 3) after the complete cohort was re-prepared. It verifies the original records and adapter weight and configuration digests (weight drift and configuration drift are distinct errors), then proves each `adapter_config.json` describes the fitted vanilla LoRA: the shared conversion validator parses it, rejects variants (DoRA, LoRA bias, layer replication, aLoRA, PiSSA-style initializers, unknown settings) and per-module rank/alpha patterns, compares rank, alpha/scaling, dropout, targets, orientation, bias and modules-to-save with the recorded recipe and targets, and checks weight tensor names and shapes. Omitted fields are reconstructed only from the documented defaults of the recorded PEFT profile (run dependencies or the config's `peft_version`; supported: 0.21); otherwise they are missing evidence. Base paths and other provenance fields are not identity. The compatibility record and every current candidate list carry weight and configuration hashes plus the normalized configuration digest, which `select` rechecks. It reconstructs the revision-2 fit, model_select and probe descriptions from the original exports by `export_id` in the original consumed order (every member must be recoverable and repeated evidence consistent) and the base content from the original pinned asset manifest (unavailable or changed assets leave eligibility unproven), and compares them with the new job. Equal fitting and monitoring inputs (path, schema or family-renaming changes) write an eligible compatibility record linking the original artifact hashes and both job identities; `select --compatibility` then validates the candidates through its normal objective, base, adapter and identity checks. Changed fitting inputs require a refit; a changed monitoring or selection plan writes a record stating that the weights remain compatible but the original shortlist cannot be claimed for the new protocol (a new fit reproduces it); a role overlap from new family closure fails re-preparation; loss-v1 runs cannot be relabelled; missing evidence fails with the fields needed. Acceptance-only changes rerun policy fitting at selection. Originals and historical check exposure are never modified; selecting with the original compatible toolchain remains a separate option.
